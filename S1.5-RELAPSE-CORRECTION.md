# S1.5 / P0 — Relapse firmware correction and root-cause boundary

## Correction

S1.4 incorrectly said that `relapse-aio-multi-wait` was a PS5-only case fixed in 14.00 and
therefore absent from PS4 FW 13.52. The PS5 range in the local corpus does not establish the PS4
range. PSDevWiki separately names a PS4 AIO vulnerability "relapse", gives the range
`?5.00?–13.52`, and attributes a PS4 13.02–13.52 implementation to raw13g.[3] The exploit-chain
table makes the binding explicit: `13.02–13.52 → relapse → slopkit → raw13g`.[4]

That establishes **family attribution and firmware applicability**, not the root cause. The same
PSDevWiki section has no implementation/write-up and says only `Bug Description: To be
documented`.[3]

## What raw13g itself establishes

At Git commit `9ba675b554b787bf043b08f24614b1bb9086672c`:

* the 13.52 block inherits 13.50 and replaces the kernel-specific values; its status says
  `state=663-LIVE-on-hardware … bug=663`.[1]
* `jb.js` invokes `SYS.aio_multi_wait` with five arguments; the public source never uses the word
  `relapse` anywhere in its current tree or history.[2]
* the build's own gate contains `SUPPORTED = {1302, 1304, 1350, 1352}` and says all four were
  measured on hardware. This proves support of the listed exploit build, not pristine-image
  identity and not a root-cause explanation.

Therefore the name/range comes from PSDevWiki; the executable chain and syscall evidence comes
from raw13g. Neither source alone proves the full statement.

## Dispatch and byte localisation

The local `sysent` table is at RVA `0x1102b70`, stride `0x30`, with `sy_call` at `+8`:

| syscall | slot → `sy_call` VA → handler RVA | narg | independent name-table entry |
| --- | --- | --- | --- |
| 661 | `0x110a760 → 0xffffffffd01ef6f0 → 0x11f6f0` | 4 | `aio_submit` |
| 662 | `0x110a790 → 0xffffffffd01ef710 → 0x11f710` | 3 | `aio_multi_delete` |
| 663 | `0x110a7c0 → 0xffffffffd01eff50 → 0x11ff50` | 5 | `aio_multi_wait` |
| 664 | `0x110a7f0 → 0xffffffffd01f0c50 → 0x120c50` | 3 | `aio_multi_poll` |
| 666 | `0x110a850 → 0xffffffffd01f1150 → 0x121150` | 3 | `aio_multi_cancel` |
| 669 | `0x110a8e0 → 0xffffffffd01f19c0 → 0x1219c0` | 5 | `aio_submit_cmd` |

The independent name table at RVA `0x1a63200` and raw13g's syscall map agree. Thus
`bug=663 → aio_multi_wait → local handler 0x11ff50` is **PROVEN as dispatch identity**.

It is **not** proof that the vulnerable instruction or lifetime violation is inside the small
wrapper at `0x11ff50`; the wrapper reads five arguments and transfers control to deeper code.

## Detector reproducibility, measured before consulting the public implementation

The frozen FW 13.52 scan contains:

* `D3_lock_coverage` at `0x11ff50`, rank 2, `RACE_UNLOCKED_SHARED_WRITE` — six lock calls and one
  uncovered store;
* two `D2_double_release` findings at `0x11f710` (syscall-table slot 662), rank 3;
* no finding at `0x11f6f0` (syscall-table slot 661).

This is **detector localisation reproducibility**: PS4RF independently placed a top-ranked
concurrency candidate on the same syscall handler. It is not root-cause reproduction. D3's own
counter-evidence says the object is not proved shared; object-flow analysis at `0x11ff50` also
refuses because the wrapper contains no recognised refcount-drop site.

## Exact remaining proof obligation

Reconstruct the wait/cancel lifetime path below `0x11ff50`: object allocation, registration in the
AIO wait structures, timeout/error unlinking, concurrent `aio_multi_cancel` access, final release,
and the stale consumer. The proof requires one object identity across those functions plus an
ownership/lifetime contradiction. Until then the actual PS4 Relapse root cause remains
**UNKNOWN**, not inferred from the public exploit's behaviour.
