# P4/W17 — PS4RF primitive migration: generic surface, experiment layer, profile revision

**Status: OFFLINE COMPLETE (W17 / W17-D / W17E / W17F).** This document is the review reference for
the frozen-core drift revision it introduces (the `R4` entry in `FREEZE-DRIFT.md`) and the record of
the two migration waves that changed the operation surface, the promoted profile and the
deterministic generators.

---

## 1. What W17 changed and why

W17 replaces the "one frozen standalone payload per research question" model with two *generic*
PS4RF operations that the experiment layer drives:

| wave | commit | content |
|---|---|---|
| W17 | `f4b8ba7` | PS4RF experiment layer (Q6 + OWN-1) with frozen-payload oracle parity |
| W17-D | `a186f4b` | native bounded snapshot recipe + generic ioctl provider (offline, no live step) |
| W17E | `9e4c576` (partial) | generic primitives + experiment-layer refactor; the op revision `R5` **prepared, not applied** |
| W17F | this branch | profile migration, semantic parity instead of magic counts, D18 drift, historical/current identity split |

The two new primitives replace per-question payloads:

* `kernel.snapshot.recipe` — one bounded, profile-defined recipe walk (`RVA_READ` plus one
  `FOLLOW_ONCE` level, 16 entries max, 4096 bytes per read), executed by
  `native/target/ps4rf_recipe.c` against an injected read callback, so the identical provider code
  runs under the offline harness and on the console. The request carries a `recipe_ref` (a *name*
  resolved in the compiled table) and optional bounded `indices`; **no raw address is expressible**
  in the request, and the provider has no `FOLLOW` loop other than the single declared level.
* `ioctl.invoke` — an explicit device policy with a command allowlist
  (`native/target/ps4rf_ioctl_policy_data.h`: one device, three commands, fixed 24-byte argument
  blocks, fixed max blob), open → ioctl → close with rc/errno/output reported. No arbitrary kernel
  call, no address argument, no unbounded buffer.

Neither provider carries experiment-specific logic: the recipe/command *data* is generated
(`native/target/gen_recipe.py`, `ps4rf_ioctl_policy_data.h`) from the experiment fixtures, and a
test greps both provider sources for experiment vocabulary and fails on any hit.

## 2. Operation surface (the core drift this revision documents)

Two operations were added to the frozen registry (`core/rpc/registry.py`):

| operation | capability | args (generated) | target route |
|---|---|---|---|
| `kernel.snapshot.recipe` | `kernel.read` | `recipe_ref` (required), `indices` (optional) | `privileged_provider`, wired |
| `ioctl.invoke` | `ioctl.invoke` | `device`, `command`, `blob` (required), `mode` (optional) | `privileged_provider`, wired |

The authoritative capability catalog (`core/capabilities/catalog.json`) gains the name
`ioctl.invoke` — the *final* catalog digest for this surface; the catalog stays a plain name list
(route/provider authority remains in `tools/dispatch/matrix.py`, deliberately not duplicated).

Counts move with the revision and are **generated, never copied**: registry and W3 interface table
38 operations, target table 38 rows (19 wired / 19 deferred), 55 argument rows, target route counts
`stub=17 mock_only=4 deferred_privilege=13 deferred_host_chain=1`.

`kernel.snapshot` itself is **not** re-purposed here: its frozen alias/argument form is untouched,
its raw explicit-range form stays deferred on the target, and the planned op revision `R5`
(de-aliasing `kernel.snapshot` onto the recipe form together with the W15 release/index-bound/
response-form machinery) is **not applied** by this wave. Its three acceptance tests stay `xfail`
(strict) in `tests/test_w17e_schema_isolation.py` and are the unblock list for a later revision.

## 3. Profile revision (FW13.52)

The production profile `profiles/fw1352/profile-13.52.json` gains exactly two `operation_policy`
entries (`kernel.snapshot.recipe`, `ioctl.invoke`) with `locator_ref: null` and
`profile_required: true` — the selector is the `recipe_ref` / `command`, not a locator. Nothing else
in the document changes (verified with a parsed-JSON structural diff: every other section identical
and every pre-existing policy entry byte-identical). The generated profile fixtures
(`tests/fixtures/profiles/`) and the operation matrix are regenerated by `gen_profiles.py`; their
pins move with the generator, never by hand.

## 4. W17F — the migration itself

W17F is the wave that made the *correct* new surface stop reading as a broken one. The classes of
failure and their fixes are all the same root cause: a historical number or a historical identity
had been promoted into an authority.

* **Magic counts removed** in `tools/primitive_iface/schema.py`, `tools/dispatch/matrix.py`,
  `native/target/gen_optable.py`, `native/target/build_manifest.py`, `tests/test_w14_daemon.py`,
  `tests/test_target_build.py`, `tests/test_primitive_interfaces.py`,
  `tests/test_provider_wiring.py`, `tests/test_differential_harness.py`: every parity assertion is
  now *set equality against the authoritative surface* (schema `OPS`, the generator's
  `TARGET_WIRED_OPS` plus the named `TARGET_ROUTE_OVERRIDES`, the gate's `privilege_gated_ops()`),
  with the difference printed when it fails. No new count became the new authority.
* **Historical vs current identity split** (the W17F/`c3d0210` and `aa9448d` rule): transcribed
  owner records validate against a named `TRANSCRIBED_PROFILE_SHA` (the profile identity that was
  authoritative when they were captured), synthetic and current paths keep deriving their hash from
  the promoted profile. Recorded bytes are never rewritten.
* **Boot identity**: `tests/test_boot_identity.py` recomputes the recorded W10/W11 capture boot id
  from the *historical* profile identity (`CAPTURE_PROFILE_SHA_W11`) and proves, in a second test,
  that the current promoted profile is a different identity — so a future profile revision can
  never silently rewrite live evidence, and the current side never needs a re-pinned literal.
* **D18 drift**: the two core files of this revision are documented in `FREEZE-DRIFT.md` under
  revision `R4`; the manifest `SHA256SUMS` stays byte-identical (never re-issued).

## 6. What this wave does **not** do

No live action of any kind: no upload, no console contact, no loader-port activity. `kernel.snapshot`
keeps its deferred route; the gated operations keep `provider_entry = false`; no §70 approval is
claimed by this document for a live run of the two new primitives.
