# P4 / W11.2 — fixed privileged boot identity read

W11.1 closed the userland path to a boot instant: `sysctlbyname("kern.boottime")` and
`sysctl({CTL_KERN, KERN_BOOTTIME})` both fail in the size query with `rc = -1` / `errno = ENOENT`
and never return a byte. W11.2 therefore reads the one thing that is already pinned by offline
evidence (W10): the `struct timeval` inside the FW13.52 kernel image at `kbase + 0x224C6C8`.

This is **not** a generic `kernel.read`. It is a single fixed region, a single callback, a single
`kexec`, and the host re-derives everything that could otherwise be believed on trust.

## What the wave is allowed to do

| Mandate | Implementation |
| --- | --- |
| exactly one fixed source | `PS4RF_BOOTREAD_SOURCE_RVA 0x224C6C8u`, `PS4RF_BOOTREAD_READ_LEN 16u` in the kernel section of `native/target/ps4rf_bootread.c` |
| one shot, guard before `kexec` | `g_ps4rf_bootread_called = 1` before the single `kexec((void *)&ps4rf_bootread_kpayload, info)` |
| no retry, no second callback, no loop over addresses | one call site, one callback symbol, fixed RVA |
| kbase only as in W9 | `rdmsr(LSTAR)` → shape gate (canonical range, page offset `0x1C0`) → `LSTAR - 0x1C0` → cross check against `get_kernel_base()` **before any byte is read** |
| read flow | 1. base 2. shape/cross check 3. fixed address 4. exactly 16 bytes into the payload's own result block 5. no further kernel memory operation 6. return |
| no writes | no `wrmsr`, no kernel memory write, no arbitrary copy, no function pointer from the host, no syscall table change, no patch, no allocator, no locking, no persistent state |
| bounded result | fixed-layout `ps4rf_bootread_info`, same buffer that `kexec` receives (`info` directly, not wrapped) |

A callback that stops early still says so: `magic_out` marks "the callback body started", the
`guard` canary marks "the read completed", so an event can never claim a measurement that was not
made (and the host rejects the event if it does).

## Host side: what is re-derived

`tools/hostctl/bootpriv.py` turns the event's raw numbers into a verdict, or refuses. The event is
first checked as a *contract* (mandated fields, the no-write / no-host-address / no-boot-id-claim
flags, one 16-byte read from the frozen RVA, the payload's `tv_sec`/`tv_usec` and its validation
status must equal what the raw bytes decode to). Two very different negative results exist and are
reported differently:

* **contract violation** — the reported numbers disagree with each other, leave the frozen source,
  or claim something the payload may not claim. The event is untrusted: `verified: false`, no boot
  id, and **no verdict is derived from it**.
* **failed read** — a valid, host-verified fail-closed outcome: `verified: true`, `no_boot_id:
  true`, `outcome` naming the exact stage (`CALLBACK_NOT_EXECUTED`, `KEXEC_FAILED`,
  `LSTAR_SHAPE_INVALID`, `KBASE_CROSS_CHECK_MISMATCH`, `TIMEVAL_*`). The measured raw values are the
  finding; the wave stops there.

Only when both are clean does the host decode the timeval from the raw bytes itself, apply the
refusal rules (`tv_sec > 0`, `0 <= tv_usec < 1_000_000`, boot instant not after the console wall
clock), build the canonical object with the **real promoted profile hash**, hash it
(`ps4rf.boot-binding.v1`) and publish `BOOT-` + the first 16 lowercase hex characters. The payload
says `boot_id_claim: NONE`; it never forms an id.

## Event and session contract

Sealed event `boot.binding.privileged`, schema `ps4rf.boot.binding.privileged.v1`
(`tools/hostctl/session.py`): typed accessor `session.boot_binding_privileged`, its own required
field set, same single-reader routing and same fail-closed schema accounting as every other event
(`EVENT_SCHEMA_REJECTED` with the reason instead of a silent `null`). The event carries
`callback_executed`, `kexec_rc`, `lstar`, `kbase_candidate`, `kbase_sdk`, `cross_check`,
`source_rva`, `read_length`, `raw_hex`, `tv_sec`, `tv_usec`, `validation`, plus the honest flags
(`single_callback`, `retry`, `writes_to_kernel`, `host_supplied_address`, `generic_read_primitive`,
`boot_id_claim`).

## Offline proofs (no console involved)

* `python -m tools.hostctl.bootpriv selftest` — the verification rules: one valid event, six
  fail-closed outcomes, twelve contract violations (lying bytes, wrong RVA, short read, claimed
  boot id, retry claim, missing field, …). Each violation must leave the event untrusted.
* `python -m tools.hostctl.cli selftest --w112-privileged-boot-read …` — the whole chain against the
  host agent build: agent → sealed event → central router → host verification → evidence. On a host
  there is no kernel, so this is exactly the fail-closed path (`kexec` fails, no boot id) and the
  run is expected to be recorded as a decisive, verified outcome.
* `python tools/profiles/w11_2_gate.py` — the W4/W5/W7 gate path before and after a binding: the
  boot reason (`BOOT_BINDING_MISMATCH`) becomes `PROFILE_MATCH`, while `kernel.read` stays
  `OPERATION_DEFERRED` with its `LOCATOR_MISSING` detail — no capability promotion is implied by a
  boot identity.
* `tests/test_w11_2_boot_read.py` — host verification, the independent digest/boot id derivation,
  the “no boot id without a complete read” rule, the payload-never-claims-an-id invariant, the
  frozen source region, the one-shot guard ordering, the gate report and the session contract.

## Cross check with the W10 capture

The pinned W10 instant (`sec 1789910256`, `usec 860896`) is **historical comparison evidence only**.
The host reports whether the live value matches it, but a live run is expected to differ: a
different boot has a different boot instant, and that difference is the point.

## Manifest gates (`gate_bootread`)

`native/target/build_manifest.py` runs `gate_bootread()` for `--profile w11.2` (the profile
`build_ps4.sh` selects when `PS4RF_TARGET_BOOTREAD=1`). The gate reads the linked ELF (`objdump -d`,
`nm -P`), the module sources and the SDK, and appends every deviation to the manifest's `problems`,
so a failure flips the manifest verdict to `FAIL` and stops the build. Nothing is taken from the
sources alone: each structural claim is measured on the artefact, and the observed counts,
addresses and offsets are stored under `gates.bootread` (source sha256s included) so a reviewer can
re-run the check. `--repro-elf <second ELF>` additionally records the byte-identical comparison of
the two builds in the manifest; `build_ps4.sh` already builds twice and `cmp`s ELF+BIN before the
manifest step, so adding that one flag to its manifest call is all that is missing for the proof to
travel inside the JSON.

Re-run on an existing artefact (addresses below are from ELF `207b0d71…`; they move with any source
change, the counts do not):

```sh
python3 native/target/build_manifest.py \
  --elf OUT/build-a/ps4rfd.elf --bin OUT/build-a/ps4rfd.bin --out OUT/build_manifest.json \
  --source-root . --sdk "$SDK" --expect-host 192.168.1.148 --expect-port 9028 \
  --profile w11.2 [--repro-elf OUT/build-b/ps4rfd.elf]
```

| Claim | Measurement |
| --- | --- |
| one privileged callback | kernel-section symbols are exactly `ps4rf_bootread_kpayload`, `…_k_lstar_ok`, `…_k_readmsr`, `…_k_read8`; no `ps4rf_attest*` symbol in the image |
| one `kexec`, in the user section | 2 `call <kexec>` in the whole image = 1 payload-owned site in `ps4rf_bootread_run` (`0x9b01`, passes `&ps4rf_bootread_kpayload`) + 1 SDK site inside `get_kernel_base` (`0xbbd0`); exactly one `syscall 11`, in the SDK `kexec` wrapper (`0xa493`) |
| one fixed read region | the `0x224c6c8` immediate appears exactly twice, both inside the callback — the `source_rva` echo (`0x98b9`) and the read base (`0x98eb`); every other kernel-section immediate ≥ 1 MiB must be on the documented non-address allowlist |
| read length 16 | `PS4RF_BOOTREAD_READ_LEN == 16`, loop bound `cmp $0x10` (`0x9903`), one `read8` call site in the loop, packed store `0x1000000001` (count 1 / len 16) |
| one `rdmsr`, no `wrmsr` | 36 `rdmsr` in the image = the payload leaf (1, `ps4rf_bootread_k_readmsr`) + the SDK `kpayload_kbase` that `get_kernel_base` pulls in (35); 0 `wrmsr` |
| callback calls nothing else | call targets are exactly the three module kernel-section leaves (`readmsr`, `read8`, `lstar_ok`, the third kept out of line by `gcc -Os`); no indirect call/jump |
| no host-supplied address or length | args struct checked against the libPS4 kernel ABI `{void *syscall_handler; <info> *info;}`, fixed info layout, fixed event key set, the agent trigger is `session.status` and reads no request field, the frozen wire sources never mention bootread |
| no retry | guard assignments are exactly `= 0` (declaration) and `= 1`; the single guard store (`0x9acc`) precedes the single `kexec` call (`0x9b01`); no `goto` |
| bounded result | derived x86-64 layout is 96 bytes (`magic_in +0x0 … guard +0x58`) and the binary agrees (clear-loop bound `cmp $0x60`, guard store `+0x58`, `magic_out` store `+0x50`, no access past `+0x58`) |

**SDK allowances.** `get_kernel_base()` is the mandated cross-check and libPS4 implements it with
its own `kexec` transition and its own kpayload (`kpayload_kbase`, 35 `rdmsr`). The gate counts the
*payload-owned* site (1 `kexec`, 1 `rdmsr`) against the mandate and fails on anything that is
neither payload-owned nor one of those two named allowances — the whole-image numbers stay in the
manifest next to the rule they are compared against.

**The gate itself found two real defects on its first run against a real build (ELF
`207b0d71…`) — both are now fixed, and the current build passes (see below):**

* `struct ps4rf_bootread_args` has a single member (`info`). The kernel builds
  `{syscall_handler, <pointer passed to kexec>}` and hands the payload a pointer to it (libPS4
  `source/payload_utils.c:45`, `include/payload_utils.h:54`, W9 harness
  `tests/harness/attest_offline.c`), so a one-field struct reads `syscall_handler` as the info
  pointer: the magic check would read kernel code and, on mismatch, write `cb_status` into kernel
  memory. Fix: declare `void *syscall_handler;` first, keep `info` second.
* no compile-time `sizeof` assertion for `ps4rf_bootread_info`.

Both fixes are in the module now: `void *syscall_handler;` is the first field of
`struct ps4rf_bootread_args` (the manifest records `args_fields: [syscall_handler, info]`), and the
result block carries its compile-time assertion. A scratch build with exactly those two changes had
already shown `verdict: PASS` with no problems, so the gate was not over-strict.

**Current state:** `PS4RF_TARGET_BOOTREAD=1 sh native/target/build_ps4.sh …` →
`verdict: PASS`, `problems: []`, `relocations 0`, `undefined_symbols 0`, reproducible twice
(`--repro-elf` → `identical: true`), ELF `f002105502c00deab9e9ff47f809c5038a129c869a0c7bc1fd93db1408bf6c24`,
BIN `6b65eea378ca008ff8852f30dc4e71bc457ff827376f5e5ea7fc31c34a0f5108` (70 420 bytes),
manifest `c787ceb737eb468f092b5a8e6976347c3adbde7eecb50d7c38d01f7ee816a46b`,
build id `7b65670b4018d920927bdc329295684f`. A scratch mutant with the one-shot guard removed flips
the verdict to `FAIL` with the two exact findings — and the real module stayed untouched
(`native/target/ps4rf_bootread.c` sha256 `a49f00091b63069b…`).

The offline harness `tests/harness/bootread_offline.c` (wired through
`tests/test_bootread_offline.py`, one child process per case) drives the **production** callback
with `kexec`, `get_kernel_base` and the weak leaf reads replaced by a synthetic kernel and reports
the eight mandated cases; it now reports **8/8, exit 0** — case A `RUN_OK` with 16 byte reads and
`cross_check MATCH`, B–D the exact `TIMEVAL_*` reasons, E `BOOT_TIME_IMPLAUSIBLE`, F
`CB_LSTAR_SHAPE` with the read counter unchanged, G `CB_KBASE_MISMATCH` with zero bytes, H
`RUN_ALREADY` with zero deltas. It was also the artefact that exposed the dispatch defect above.

## First live run (2026-10-06, one upload after a fresh rearm)

Exactly one upload of the frozen v1 payload (`6b65eea3…`) through the relay; the agent ran the whole
sequence (handshake, `status`, one-shot callback, sealed event, `CLIENT_CLOSE` BYE with cleanup
`COMPLETE` and `resources: []`), health stayed green and the loader port was never touched again.
**The privileged read itself worked on the console:**

| observation | value |
| --- | --- |
| `callback_executed` / `kexec_rc` / `cb_status` | `true` / `0` / `OK` |
| `lstar` | `0xffffffff998f41c0` (canonical, page offset `0x1C0`) |
| `kbase_candidate` / `kbase_sdk` / `cross_check` | `0xffffffff998f4000` / same / `MATCH` |
| read | `source_rva 0x224c6c8`, `read_length 16` |
| raw bytes | `7c3ac36a00000000bf620800000000` + the missing final `00` |
| decoded | `tv_sec 1791179388`, `tv_usec 549567` (a complete `timeval`), console wall clock `1791277354` |
| payload validation | `OK`; `boot_id_claim NONE` |

**The host refused the event and formed no boot id** — correctly, and that is the wave's fail-closed
behaviour working: the event claimed a 16 byte read but carried only **30 hex characters**
(`read_length says 16 but 15 raw bytes were sent`). Root cause was local and trivial: the *event
builder's* hex encoder in this module used `o + 3u < cap`, which stops before the last byte of a 16
byte read in a 33 byte buffer. The read path, the kernel section and the host verification were all
correct; the frozen W11.1 module uses the correct bound (`o + 2u < cap`) and the W9 module uses
libc's encoder, so neither is affected.

Fix (v2, offline only, no second upload): bound corrected, a regression test pins it
(`test_hex_encoder_leaves_room_for_the_last_byte`), plus the same class of failure is caught at
runtime by the host contract check whenever a payload miscounts its own bytes. Offline proof for v2:
harness **8/8**, W11.2 gate **PASS**, whole suite **552 passed / 1 skipped**, manifest `verdict PASS`
with `problems: []` and reproducible twice — ELF
`abf513799b0a49f85ac75b5fe2458fc682d583ad5646126e018a994a4da6505e`, BIN
`ec48b2fcf372f1c7296492e1a370fdffc837a60b09336a9d6947094ef6741a90` (70 388 bytes), build id
`33aa4bb225532bf33e4f1f30bb50e227`.

A further live attempt requires a **new explicit rearm**; the first run's single upload is spent and
no retry was attempted.

## Deviation W11.2-D1 and boot-identity semantics (review outcome)

**`W11.2-D1: PASSIVE_LOG_STREAM_NO_BANNER` — disposition `ACCEPTED_PROBE_DESIGN_ISSUE`.**
Port 3232 is GoldHEN's *passive* log stream: a successfully established TCP connect without an
immediate log line is not a health failure. The check is therefore `health:port-3232-connect`
(success = bounded TCP connect) and the optional `log_activity_observed` state is reported
separately, deliberately outside the verdict-bearing checks, so `false` cannot flip the target
health verdict. A longer banner wait is **not** used instead — that would keep measuring log activity
rather than service reachability. FTP (banner) and ICMP checks stay; port 9090 stays excluded from
every health check. The W11.2 live evidence packs are unchanged.

Deviation history (kept as-is, no retro-editing): the v1 run's health check passed (a log line
happened to arrive), the v2 run and the re-run timed out on the banner although the port accepted the
connection — three data points, probe design, not console health.

**Semantics of the accepted identity:**

* `IN_BOOT_STABILITY_EMPIRICALLY_PROVEN` — accepted: two independent live runs inside the same boot
  produced the identical identity (`BOOT-f0329415c5d8517d`, digest
  `f0329415c5d8517d3e20bca831343adac3b03a83be7eaa6ce4fad245964867bc`, bound to
  `profile_sha256 4a6f575c8b1aa7906d7a86d08fe5cc4e5dc1a2939a2de19fac40c7fa82771766`).
* `CROSS_REBOOT_CHANGE_EMPIRICALLY_PROVEN` is **not** claimed. It requires a second *real* boot
  identity measured after an actual console reboot; what exists today is the write-path analysis
  (`SUPPORTED_BY_WRITE_PATH_ANALYSIS`): the pinned clock-set path is the only writer of that
  variable, so a reboot should change the value — which is a hypothesis, not a measurement.
