# PS4RF — S1.9 findings: CFG soundness and D2 path semantics

Phase S1.9 on top of the frozen S1.8 baseline `f1be50e`. Scope: the default CFG, D2's
kill/slot semantics, and the dependency of the existing detectors on the incomplete CFG.
No provenance feature was added in this phase.

Vocabulary: `PROVEN`/`must` are the strong readings; `may`/`CONDITIONAL` are the weak ones.
A rank is a report priority, not a proof.

---

## 1. What was wrong (measured, not assumed)

`FunctionView._build_cfg` asked `_direct_target` for a successor and `_direct_target` answers
for `call` and `jmp` only. Every direct conditional branch therefore lost its taken edge:
alternative paths never joined, a value looked definite across a branch, and any claim of
"no path without a kill" rested on a CFG that did not contain the branch. The S1.8 handoff
already had this as its blocking item; it was left undone because restoring the edges made
`D2_double_release` claim a kill-free path on the **fixed** 13.52 `aio_multi_delete` body.

Both halves are one defect: the CFG hid paths, and D2 read a slot label as an object
identity. Fixing either alone produces a false claim, so they are fixed in one step.

## 2. CFG correction (P0)

`_build_cfg`, both modes, for a direct conditional branch (`mnemonic` starts with `j`,
target resolvable):

* taken edge to the target's leader,
* fall-through edge to the leader of the following instruction,
* exactly **one** edge when the target *is* the fall-through (`fall != taken`),
* `jmp` keeps only its direct target; an indirect `jmp` contributes no successor; `ret`
  contributes none (unchanged),
* a target outside the function is not an internal edge.

Fixture `tests/fixtures/discovery/cfg-fixtures.S`, built with the real `as`/`ld`/`objcopy`/`nm`
by `gen_cfg.py`, six shapes: two-way conditional, jump-only, branch whose target is the next
instruction, indirect jump, loop with back edge and exit, tail jump out of the function.
`tests/test_discovery_cfg.py` pins each edge; the expectation lives in the generator, i.e.
in the source, not in scanner output. Mutation check: deleting `fall != taken` makes
`same_target` fail; the file was restored from a copy afterwards.

The same fixture and test were run against the S1.8 worktree: the baseline fails them. That
is the positive control that the correction is a correction.

## 3. D2 path semantics (P1)

Three separate things were conflated in one string label:

1. **Object identity.** `_slot_identity(slot)` splits a bare register (`rbx`) from a memory
   expression (`rbx+0x40`, `(rbp-0x68)+0x18`) and returns the base registers of the latter.
   Two release sites on one slot are one object only if the identity survives the path.
2. **Object end.** `_path_without_kill` walks the corrected CFG from the first site to the
   second. The object ends when the slot is stored to, when a base register is rewritten, or
   when a caller-saved base register crosses a call; reaching another release call also ends
   it, because caller-saved arguments cannot be shown to be equal afterwards.
3. **Refcount guard.** `_guarded_release(view, site)` recognises
   `lock xadd dword ptr [obj+0x28], ecx` with a negative delta, `cmp ecx, 1` and a `jne`
   whose target lies past the release call. Such a site frees only when *this* thread
   observed the last reference; a second pass would have to observe "last reference" again,
   which is a concurrency defect, not a static double release. The guard often ends the
   predecessor block rather than the release block, so the search walks the
   single-predecessor chain backwards (at most three blocks) and stops at a join, where
   there is no linear context to read.

Release sites are labelled `PLAIN`, `CONDITIONAL` or `REFCOUNT_GUARDED`. A rank-1 claim
requires identity preservation and no guard; `may` stays `may`, and every claim carries the
`release_kinds` list plus `counter_evidence.refcount_guarded` whether or not it fires.

### The false alarm on the fixed 13.52 body, instruction by instruction

Body `aio_multi_delete`, RVA `0x11f710`, 484 instructions, 96 blocks. Two D2 groups exist:

**(a) slot `rbx`, sites `0x11fda9` and `0x11fe1b`** — the submission object. With branch
edges, a kill-free path exists (`0x11fd9f → 0x11fb8f → … → 0x11fe11`, 25 blocks, no store to
`rbx`), and it is *real*: along it `rbx` is rewritten three times —

```
0x11fb8f  mov ebx, r12d
0x11fa5b  mov rbx, qword ptr [rcx + 0x20]
0x11fbe6  mov rbx, qword ptr [rcx + r14*8]
```

so the second release consumes a **different** object. The slot label was the only thing the
two sites shared. S1.8 ranked this 1; S1.9 refuses it and names the reason
(`identity_lost`, in `claims.same_object`).

**(b) slot `rbx+0x40`, sites `0x11fd92` and `0x11fe04`** — the entry pointer. Both are
refcount-guarded:

```
0x11fd80  lock xadd dword ptr [rax + 0x28], ecx   ; ecx = -1, set at 0x11fd7b
0x11fd85  cmp ecx, 1
0x11fd88  jne 0x11fd97                            ; skips the call at 0x11fd92
...
0x11fdf2  lock xadd dword ptr [rax + 0x28], ecx
0x11fdf7  cmp ecx, 1
0x11fdfa  jne 0x11fe09                            ; skips the call at 0x11fe04
```

Each site runs only for the thread that saw the count reach zero.

**Why the guard alone does not make the firmware fixed.** The vulnerable 9.00 body has the
same guarded entry releases (`0x410e36`/`0x410e3e` and `0x410ec8`/`0x410ed0`). The labelled
defect is not a static double release at all: it is the unlocked read/take of the entry slot
that races the lock-taking path. D2 was the wrong detector for this body from the start. The
actionable finding on the vulnerable body is D1 (`use_after_release` on `rbp-0x48`, rank 1);
the fixed body stays below the actionable level. That is the gate, and it is not achieved by
tuning D2 until the negative case disappears.

## 4. Dependency of the other detectors on the incomplete CFG (P2)

| Layer | View | Depends on branch edges | Measured effect of the correction |
|---|---|---|---|
| D1, D4 lifecycle | `_lifecycle_view` → `strict_cfg=True` | no, it always had them | none: 13.52 `MAY_USE_AFTER_RELEASE` 65 / `PATH_DEPENDENT` 15 identical; 9.00 23 / 11 identical |
| D2 double release | default | yes | 1 finding demoted (rank 1 → 3), 0 promoted |
| D3 lock coverage | default | yes | +38 findings, 6 over-claims removed (see below) |
| D5, D6, D8 | default | yes in principle | 0 changes on 2 053 (13.52) and 1 091 (9.00) functions |
| summaries / ownership / chains | `_Body` default | yes | no verdict promoted; see the hop re-run |

**Ownership verdicts.** No `must` attribution exists anywhere in this phase, so no strong
claim had to be withdrawn: the S1.6 hop re-run on the corrected CFG gives
`evaluated=13 proved=0 conditional=12 refuted=0 unknown=0`, verdict `SUPPORTED`, and the
negative controls still refute (`3 refuted same-caller`, `3 other-register refusals`). The
13th evaluated call site is one where no caller argument object is attributed any more; it
is counted as evaluated and lands in no verdict bucket. The S1.8 statement "0 PROVEN hops"
holds unchanged.

**D3 over-claims found and removed.** D3 read coverage as "some lock block *dominates* the
store". After the correction 39 new findings appeared; a path witness check over their 158
stores found 152 stores with an explicit lock-free path from the entry and **6 with none** —
every path took a lock, but in *different* blocks, so no single lock block dominated the
join. Coverage is now a path property (`_blocks_without_lock`: the blocks reachable from the
entry without entering a lock block). Re-measured: 38 findings, 152 stores on a lock-free
path, 0 stores in unreachable blocks, 0 stores without a witness.
Fixture `lock-coverage-fixtures.S` pins both directions, including the explicit assertion
that the old dominance reading would have called the covered shape a bug.

## 5. What is still not claimed

* No release-site attribution reached `must`: 55 of 259 sites are attributed, all `may`.
* `D2_double_release` on the 9.00 body stays at rank 3. The body is vulnerable, but not by a
  static double release, and S1.9 does not invent a different reading to make it rank 1.
* The CFG correction is **not** a whole-program CFG: indirect jumps, `ret` targets and
  cross-function tail jumps still contribute no edge, and `jmp` through a register is still
  a dead end. Paths that need those edges remain unknown, not absent.
* The 204 unattributed release sites are untouched by this phase.
