# S1.6 — Measurement

Image: PS4 FW 13.52 `kernel.bin`, SHA-256 `cf157ffdbae872a20bbb9a46c8518b53d96c1ed75d4e73878466a295d92eca35`
(`NOT_PRISTINE`, 26 GoldHEN/Afterglow kpatch sites, syscall-table slot 11 hijacked — unchanged from
S1.5). Differential image: PS4 FW 9.00 `fw900-kernel-48m.bin`,
SHA-256 `ffe0ec65ec0ffaadf9e18675121e7df80bdddbb83a8824b3414e4cc53cbd69f8`.
Everything below is offline analysis. No hardware, no payload, no console contact.

## 1. Minimal goal — one real interprocedural ownership flow

Hypothesis H1, frozen before the run: *there is a call edge whose callee consumes a reference on
the object the caller placed in that argument register, provable from bytes alone with (a) a
caller-side placement witness and (b) a callee-side release witness.*

Search space: 106'111 direct call sites / 9'859 distinct targets (reverse index from a linear
`e8` scan) → 153 functions that consume a reference on an object passed to them → their callers.

Result: **12 witnessed interprocedural ownership transfers**, each with both witnesses, and
**6 refuted control edges**. Verdict `SUPPORTED` for the stated criterion.

Representative flow (all addresses RVA, all quotes literal):

| caller | caller witness | callee | callee witness | object |
|---|---|---|---|---|
| `0x90b0` | `0x9259 mov rdi, r14` | `0x267d10` | `0x267d33` | `arg0+0x60` |
| `0x17db0` | `0x17f2d mov rdi, r14` | `0x267d10` | `0x267d33` | `arg0+0x60` |
| `0x303f0` | `0x30405 mov rdi, rbx` | `0x267d10` | `0x267d33` | `arg0+0x60` |
| `0x30860` | `0x308d9 mov rdi, r14` | `0x267d10` | `0x267d33` | `arg0+0x60` |

The object identity is `arg0+0x60` in the callee's frame and the caller's `arg0` at the call, i.e.
the callee decrements a reference that lives in the field `+0x60` of the object the caller owns.
That is a genuine two-level ownership flow, not a call edge.

Witness completeness, stated exactly: **7 of the 12** transfers carry a caller-side *instruction*
witness (the `mov` that places the object) plus the callee release site. The other 5 carry the
object identity from the forward value chain and the callee release site, but their definition site
lies further back than the 120-instruction search window, so the placing instruction is not quoted.
They are counted as witnessed transfers; they are **not** counted as instruction-complete.

**Strength: 12 × CONDITIONAL, 0 × PROVEN.** On this kernel every consuming callee reaches its
release on a gated path (`may`), never on every path. `PROVEN` requires `must` and is therefore 0 —
reported, not rounded up.

Negative controls (same shape, must come out negative):

* same caller, different callee that consumes nothing → `REFUTED` ×3
  (e.g. `0x90b0 → 0x267b00`: "the callee is complete and does nothing with argument 0").
* same wrapper reached with a different argument register → `REFUTED` ×3
  (`rsi` carries `glob0x770f8a`, not the object).

## 2. Whole-image summary coverage (rank ≤ 2 finding functions + callees)

* functions summarised: **1'171** — `complete` 638, `partial` 530, `refused` 3.
* argument roles: `READ` 1'037, `DEREF` 488, `OUT_REF` 321, `HANDOFF` 4.
* ownership effects: `DROP_REF/may` 17, `DROP_REF/must` 0, `FREE/must` 0.
* hop evaluation over those functions: 93 `REFUTED` edges, 0 `PROVEN`.
* sequential double-release shapes (generic detector): **0**.

## 3. Why so few — attribution census

266 direct calls to a release anchor (`fdrop_release` `0xc28d0`, `free` `0x96e0`) occur inside the
354 rank ≤ 2 finding functions. Of those 266 call sites:

* **7 (2.6 %)** have an attributable object in the argument register,
* 259 do not: 229 unknown register content, 30 callee results.

Cause classes at the site (nearest definition of `rdi`, 14-instruction window): callee-saved
registers holding global/array-derived values 160, frame slots 56, direct argument 20, register
copies 12, rip-relative globals 6, immediates/other 3.

The objects this kernel releases are fetched from **global tables with scaled indices**
(`[rax + rcx*8]`) or from callee results (`getsock_cap()`-like). A scaled-index element is a
*class* of objects, not one object, so the layer refuses it rather than inventing an identity.

## 4. Chain dimensions (regression against S1.5)

370 chains, identical to S1.4/S1.5: **211 `CFG_REACHABLE`, 159 `UNREACHED`**, `compose_errors: {}` —
S1.5 is reproduced exactly.

Ownership dimension, now fed by the summaries:

* S1.5: `UNKNOWN` 370, `PROVEN` 0.
* S1.6: `REFUTED` **201**, `UNKNOWN` 161, `CONDITIONAL` **8**, `PROVEN` 0.

201 chains now carry a *negative* ownership statement (a complete body that consumes no reference)
instead of nothing. That is new information, and none of it is an upgrade to a higher proof level.

## 5. Differential: FW 9.00 (pre-fix) vs FW 13.52 (post-fix), netcontrol

The netcontrol handler was located by its published command constants (`0x20000003`,
`0x20000007`) purely to *find* it; no rule knows those values.

* `0x20000003` has **41 byte hits in both images** — the constant is not selective, so its
  containing "functions" include mis-sized inventory records. It cannot be used as a locator.
* Attributed release sites in the located candidates: **0 in 9.00, 0 in 13.52**.
* Double-release shapes: **0 in both**.
* Structural difference, recorded but not interpreted: 13.52's `0x4cb060` shows two global objects
  (`glob0x1a5a120`, `glob0x22d1d50`) while the corresponding 9.00 candidate `0x4c5f29` shows only
  `arg1`.

**Verdict: UNKNOWN.** The rules distinguish a buggy from a corrected object life cycle on the
controlled fixtures (§1 controls, `tests/test_discovery_summaries.py`), but on this real image pair
the layer attributes too few sites to discriminate. This is not evidence that the netcontrol defect
is absent or present.

## 6. `aio_multi_wait` (syscall-table slot 663, handler `0x11ff50`, narg 5)

* summary: `complete`, 3'120 bytes, 0 indirect calls.
* ownership effects: **none**. Objects seen: `arg0`, `arg0+0x8`, `arg1`, `glob0x275cea0`, reads only.
* double-release shapes: **0**.
* call edges: 12 direct, including `malloc` (`0x9520`) and `printf` (`0x2e0510`); no callee reports
  an ownership effect on what it is handed.
* return: `NEW_OBJECT` (a callee result) — ownership deliberately not claimed.

**Verdict: UNKNOWN.** No lifetime witness for the alleged waiter-array UAF. Per the S1.6 brief this
is *not* a root-cause confirmation, and the handler's own body shows no array-index write pattern
that would support the described mode-0 node sharing on this build.

## 7. Timings per phase (measured, not estimated)

| phase | wall clock | notes |
|---|---|---|
| environment + index load (13.52) | 0.11 s | cached image/index |
| reverse call index (42 MiB, `e8` scan) | 0.07 s cached / 1.05 s cold | 198'551 candidates → 106'111 sites |
| wrapper identification | **66.7 s** | 9'859 targets summarised — the bottleneck |
| hop evaluation (52 caller summaries) | 0.80 s | forward value chain per call site |
| negative controls | 0.01 s | |
| whole-image coverage stage (§2) | ~14 min | 1'171 summaries + hop evaluation |
| test suite `tests/test_discovery_summaries.py` | 0.2 s | 32 tests |
| test suite `-k discovery` | 86 s | 247 tests |

The bottleneck is per-target summarisation during wrapper identification, at ~6.8 ms per function
body: two full body interpretations plus a dominator set and a replay for the register map. That is
the next thing to optimise, not the number of findings.
